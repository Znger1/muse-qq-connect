# 把 qq-reader 接入 Muse（或任何带定时任务 + Shell 的 AI 助手）

这份文档只讲**连接机制**：AI 助手如何通过一条 SSH 命令调用
服务器端的拉取脚本、如何解读它的输出、状态保存在哪里、异常
如何处理。下层的数据库读取（取钥、解密、增量拉取）由仓库根
目录的脚本完成，原理见 [../README.md](../README.md)；系统全
貌见 [ARCHITECTURE.md](ARCHITECTURE.md)。

> 本文以 Muse 的定时任务（cron）为例。任何"能按计划触发、
> 能执行 shell/SSH"的助手平台都可以照此模式接入。

消息的筛选与提醒规则由使用者在助手侧自行定义，不属于本流
程的一部分，本文不涉及。

## 总体模式：无状态调用 + 服务器端状态

- **服务器端脚本是无状态接口**：`patrol_pull.py` 每次被调用
  时独立完成"复制副本 → 解密 → 按水位线增量提取"，把结果打
  到 stdout。它不判断消息重要性，也不发任何通知。
- **状态只存在服务器端**：钥匙、水位线、群名映射都在 QQ 主
  机的工作目录里（见下表），脚本自己维护。助手侧不需要保存
  任何跨轮状态。
- **助手只消费 stdout 的 JSON**，其余文件一概不碰。需要改读
  取行为时改脚本或配置，不要在运行时手工编辑状态文件。

## 调用方式

一条 SSH 命令（免密密钥登录，脚本路径与工作目录权限 700）：

```bash
ssh <user>@<qq-host> 'python3 /path/to/patrol_pull.py'
```

首次接入前，先在 QQ 主机上完成部署（见根 README"部署步
骤"）：生成 `key.json`，并跑一次 `patrol_pull.py` 完成水位
线初始化（只建水位线、不输出历史）。之后把它挂到助手的定
时任务上即可，周期由使用者设定（例如每 10 分钟）。

这套部署通常由助手自己完成：助手按上述清单在 QQ 主机上部
署脚本、取钥、验证并初始化水位线，人只负责提供主机、扫码
登录与关键批准（见根 README“让 Muse 帮你部署”一节）。

助手每轮的机械动作序列：

1. 定时触发，执行上面的 SSH 命令；
2. 读输出第一行（状态行），确认管线状态；
3. 逐行解析其后的消息行（JSON），交给后续处理；
4. 本轮结束。异常按"故障处理"一节走。

## 输出契约

输出为 JSON 行：**第一行是状态行**（`type=status`），其后
每行是一条新消息（`type=message`）。

状态行关键字段：

| 字段 | 含义 |
|---|---|
| `status` | `OK` 正常；`INIT` 水位线刚初始化、本轮无消息；`KEY_FAIL` 钥匙失效且自动重取失败；`ERROR` 副本/解密/解析异常 |
| `new_messages` | 本轮新消息条数（`status=OK` 时） |
| `qq_running` | QQ 主进程是否在运行 |
| `db_mtime_cst` | 数据库副本的更新时间（配置时区字符串）；长时间不更新疑似掉线/掉登录 |
| `key_recovered` | 本轮是否由脚本自动重扫内存换钥恢复 |

消息行字段：

| 字段 | 含义 |
|---|---|
| `source` | `group`=群消息，`c2c`=私聊 |
| `group_id` / `group_name` | 群号 / 群名（`group_name` 可能为 null = 尚未进映射的未知群）；私聊时看 `peer_uin` / `peer_uid` |
| `sender_uin` / `sender_uid` | 发送者 |
| `sender_is_self` | 是否为账号本人发送 |
| `send_time` / `send_time_cst` | 发送时间（unix 秒 / 配置时区字符串） |
| `text` | 消息全文。`text_source=fts`（FTS 展平文本）或 `proto`（40800 解析）均为完整正文；正文为非文字内容时 `text` 为空 |
| `has_nontext` / `nontext_types` | 是否含非文字元素及其类型：image 图片、video 视频、file 文件、voice 语音、face 表情、reply 引用、ark-card 卡片、gray-tip 系统提示 |
| `at_uids` / `at_all` / `at_me` | @ 的目标 uid 列表 / 是否 @全体成员 / 是否 @ 账号本人（脚本按配置的 uid 精确判定） |
| `unparseable` | 该条消息内容无法解析（凭输出无法得知其内容） |

## 存在服务器端的状态（助手不要碰）

| 文件 | 内容 | 说明 |
|---|---|---|
| `key.json` | 数据库钥匙 | 600 权限；只由脚本使用，不要读取、打印或搬运它的内容 |
| `watermark.json` | 增量水位线 | 脚本自己维护；手工修改会导致重复输出或漏输出 |
| `group_map.json` | 群号 → 群名映射 | 由 `group_info.db` 自动维护；消息行里的 `group_name` 来自这里 |
| `identity.json` | 账号本人的 uin/uid 缓存 | 脚本判定 `at_me` / `sender_is_self` 用 |
| `runs/` | 每轮的工作副本 | 仅保留最近 2 轮，自动清理 |

## 故障处理

| 现象 | 可能原因 | 处理 |
|---|---|---|
| `status=KEY_FAIL` | QQ 重新登录后钥匙已换，脚本自动重取（重扫进程内存）也失败 | 先确认 QQ 进程在运行且已登录；仍不行时手动重跑 `scan_key.py` / `strong_scan.py` 生成新 `key.json` |
| `status=ERROR` | 副本/解密/解析异常 | 记录错误原文，检查工作目录空间与权限后重试 |
| `qq_running=false` | QQ 进程不在（崩溃或被关） | 按部署方式拉起官方客户端；若停在登录界面，不要代填密码、不要强行登录，交由账号本人处理 |
| 数据库更新时间长时间未变 | 疑似掉线/掉登录 | 同上：先确认进程与登录状态 |
| 某条消息 `unparseable=true` 或正文为空的非文字消息 | 图片/文件/语音等在数据库里没有正文 | 输出契约本身到此为止；如需看内容，只能人工打开 QQ 界面查看（操作要点见 [../examples/patrol-loop.example.md](../examples/patrol-loop.example.md) 的"确认登录状态"一节） |
| `group_name=null` | 新群尚未进映射 | 映射会随 `group_info.db` 更新自动补齐；需要立即识别时可人工在 QQ 界面按群号查找 |

## Token 经济学：为什么增量拉取适合挂在助手上

- **筛选在服务器端完成**：解密、增量、字段提取都在 QQ 主机
  本地进行；助手每轮拿到手的只有"新消息的 JSON"，通常几条、
  经常是零条。
- **空轮次成本 ≈ 一次 SSH 往返 + 一行状态 JSON**。没有新消
  息的轮次，助手读完状态行就结束，不打开任何界面、不截任何
  图——单轮成本与"有没有新消息"成正比，而不是固定开销。
- 对照组是"截图巡查"：每轮都要截屏、用视觉读图、点开会话，
  无论有没有新消息都烧掉大量 token，且慢。本文的管线把消息
  变成结构化文本，助手直接读 JSON 即可。
