# 系统架构：Muse 接入 QQ 的连接与读取管线

本仓库提供的是**一整套连接流程**： AI 助手（下文以 Muse 为
例）通过 SSH 调用部署在 QQ 主机上的读取脚本，把你自己账号的
QQ 新消息以结构化 JSON 的形式取回。数据库读取（`patrol_pull.py`
等脚本）是这套系统的底层；上面是传输（SSH）与调度（助手的定
时任务）。消息取回之后如何处理，由使用者在助手侧自行定义，
不在本流程范围内。

## 组件图

```
┌─────────────────────────── QQ 所在主机（Linux 服务器） ───────────────────────────┐
│                                                                                  │
│   官方 QQ 客户端（3.2.34，正常登录）                                              │
│        │ 收到消息，自动写入本地数据库                                             │
│        ▼                                                                          │
│   本地加密数据库（SQLCipher）                                                     │
│   nt_msg.db（消息本体） / group_msg_fts.db（全文索引） / group_info.db（群名）    │
│        │                                                                          │
│        │  读取端脚本（全部在本机运行，只读，零网络）                               │
│        │  · 取钥：读 QQ 进程内存 → 候选钥匙 → 用库副本第 1 页 HMAC 验真           │
│        │  · 解密：只解副本（1024 字节头 + SQLCipher + WAL 盐代际过滤）            │
│        │  · 增量：watermark.json 水位线，只输出上轮之后的新消息                   │
│        ▼                                                                          │
│   patrol_pull.py ──► stdout：JSON 行（1 行状态 + N 行新消息）                     │
│        ▲                                                                          │
│        │  状态文件（key.json / watermark.json / group_map.json）只留在这台主机    │
└────────┼──────────────────────────────────────────────────────────────────────────┘
         │ SSH（一条命令远程执行脚本，只回收 stdout 的 JSON）
         │
┌────────┴──────────────────── AI 助手所在环境 ───────────────────────────────────┐
│                                                                                  │
│   定时任务（周期由使用者设定）                                                    │
│        │ 触发                                                                     │
│        ▼                                                                          │
│   AI 助手（Muse）                                                                │
│   1. SSH 运行 patrol_pull.py，读取 JSON 输出                                      │
│   2. 先看状态行（OK / INIT / KEY_FAIL / 掉线疑似）                                │
│   3. 逐行解析新消息，交给使用者在助手侧定义的后续处理                             │
│   （异常时可人工打开 QQ 界面确认登录状态，见 examples/patrol-loop.example.md）     │
└───────────────────────────────────────────────────────────────────────────────────┘
```

## 设计原则

1. **只读是结构性的，不是纪律性的。** 整条管线里没有发送、删
   除或修改消息的代码路径：读取端只 `read`/`copy` QQ 的文
   件、只解副本；助手侧只有"取回输出"这一个动作。不是"保证不
   乱发"，而是"根本发不了"。
2. **文字优先。** 绝大多数消息是文字，数据库直读又快又准。图
   片/文件/语音等非文字内容不在数据库正文里，管线只报出其类
   型与元数据（见 README"已知局限"）。
3. **增量水位线，空轮次近乎免费。** 服务器端脚本自己维护水位
   线，助手每轮只看到"上轮之后的新消息"。没有新消息时，一轮
   只消耗一行状态 JSON——绝大多数轮次没有新消息，也就不产生
   任何实质的 token 消耗。
4. **钥匙只存在于内存。** 数据库钥匙是登录时服务器下发、只在
   QQ 进程内存里的值；取钥靠读内存 + 密码学验真，不落任何凭
   据文件，不碰 `login.db`，不做协议登录。
5. **敏感数据不离开 QQ 所在主机。** 钥匙、明文库、水位线、群
   名映射全部只存在 QQ 那台机器的受控目录里；SSH 只把"新消息
   的 JSON"带出来，不搬运数据库。
6. **失效有明确状态，不静默。** 钥匙失效、数据库长时间不更新
   （疑似掉线）等异常都有明确的状态行输出与处理路径（见
   docs/MUSE-INTEGRATION.md 的故障处理），不会假装一切正常。
7. **管线与决策解耦。** 读取端只输出结构化数据，不内嵌任何筛
   选规则；状态全部集中在服务器端的几个文件里，助手侧无状态。

## 为什么不用 NapCat / WeQ 这类方案

市面上的 QQ 机器人框架（NapCat、LLOneBot 等）和一些"聊天记录
导出/查看"工具（WeQ 等）也能拿到消息，但它们的工作方式是
**注入 QQ 进程或模拟协议登录**：

- 它们拿到的是一个**能以你的账号身份行动的会话**——能发消
  息、能改群设置、能做一切账号能做的事。哪怕你只用它读消息，
  风险敞口也是整个账号。
- 注入/协议登录是腾讯风控的重点对象，**封号风险真实存在**，
  且与"用不用它发消息"无关——异常登录行为本身就会被检测。
- 部分工具的核心组件闭源，无法审计它在你账号上到底做了什么。

本方案的取舍正好相反：**不碰登录、不注入、不联网**，只读你
自己机器上、你自己账号落盘的数据副本。代价是只能读"本地已
同步的消息"、非文字内容看不到——换来的是连接方式本身不引入
账号风险。

## 组件清单

| 层 | 组件 | 位置 |
|---|---|---|
| 数据源 | 官方 Linux QQ 3.2.34 + 本地加密库 | QQ 主机 |
| 读取端 | `scan_key.py` / `strong_scan.py`（取钥）、`qq_crypto.py`（解密原语）、`decrypt_db.py`、`parse_proof.py`、`patrol_pull.py`（增量拉取）、`mention_search.py`（历史提及搜索） | QQ 主机 |
| 传输 | SSH 远程执行 + stdout JSON 行 | 两机之间 |
| 调度 | 助手平台的定时任务（如 Muse 的 cron） | 助手环境 |
| 后续处理 | 使用者在助手侧自行实现 | 助手环境 |

更细的接入步骤见 [MUSE-INTEGRATION.md](MUSE-INTEGRATION.md)；
读取端各脚本的原理与用法见仓库根 [README.md](../README.md)。
